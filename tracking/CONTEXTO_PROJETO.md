## 📊 O Que É a UNIQ

A UNIQ é uma **Consultoria de Transformação Digital com IA** para microempresas de Suzano/Alto Tietê.

**Modelo:** Done-For-You (DFY) — o cliente não toca em tecnologia. A UNIQ instala um **Parceiro Digital (MEL)** na operação do parceiro, configurado para atender, vender, qualificar leads e organizar a operação no automático.

**Tagline:** *"Multiplique suas vendas sem aprender tecnologia."*

**Nova realidade:** o Parceiro Digital é entregue através da **Base UNIQ**, uma plataforma multi-tenant onde cada parceiro acessa sua operação, conversa com a Melissa e recebe módulos ativados conforme sua necessidade.

### 🧠 O Cérebro Operacional
> **"A UNIQ vira o cérebro operacional do negócio do parceiro."**
>
> Nós não indicamos melhorias e saímos de cena. Diagnosticanos o negócio, planejamos as soluções e construímos dentro da Base UNIQ — automatizando atendimentos, eliminando gargalos, integrando processos e desenvolvendo o empreendedor.
>
> O "como" muda conforme aprendemos com cada parceiro. O "que" permanece: **transformar microempresas de Suzano em operações digitais que funcionam 24h.**

### Por que ondas funcionam (leitura do CEO)

O gargalo nunca foi vender 8 co-fundadores — é **entregar 8**. Dividir em ondas resolve isso porque:

1. **A onda 1 paga o aprendizado.** Os 4 primeiros revelam o que é padrão e o que é específico de cada ramo.
2. **A pausa não é ociosa — é a sprint de productização.** É nela que o "lego" é de fato construído, a partir do que a onda 1 ensinou.
3. **A onda 2 deve ser mais rápida e mais cara.** Se a onda 1 gerou cases, a onda 2 entra com preço maior e entrega menor.
4. **Casa com o calendário real:** onda 2 em jan/2027 → cases prontos antes da saída do CLT (fim de mar/2027) → lançamento oficial em jul/2027.

## 🧱 Arquitetura de Módulos: default + vertical

> ✅ **Princípio definido pelo fundador (07/09/2026).**

A meta é ter módulos **100% reutilizáveis**. Quando um cliente precisa de algo muito específico, cria-se uma **variante vertical** do módulo default — nunca um módulo isolado.

```
CRM              ← módulo default, base de toda operação
└── CRM_OTICA    ← variante vertical, específica para óticas
```

| Camada | O que é | Para quem |
|--------|---------|-----------|
| **Módulo default** | Funciona para qualquer microempresa (ex.: `CRM`) | Todos os parceiros |
| **Módulo vertical** | Default + especificidades do ramo (ex.: `CRM_OTICA`) | Parceiros daquele nicho |

### Por que esse modelo é forte
- **Não fragmenta a base:** o vertical herda do default, não o substitui.
- **Vira ativo de venda:** ter `CRM_OTICA` pronto permite abordar **todas as óticas de Suzano** com um case do mesmo ramo.
- **Compõe prova social por nicho:** depois de 2–3 óticas, a UNIQ domina um vertical inteiro.

### ⚠️ Regra de proteção (crítica para as 16h/semana)

> **Um módulo vertical só é construído se for replicável para pelo menos 2–3 negócios daquele nicho em Suzano/Alto Tietê.**
>
> Pedido específico de um único cliente que não se replica **não vira módulo vertical** — vira customização. E customização ou é cobrada à parte, ou é recusada.
>
> Sem essa regra, cada co-fundador vira um projeto único e a reutilização nunca acontece.

## 🔄 Dogfooding: a UNIQ opera a si mesma na Base UNIQ

> ✅ **Decisão do fundador (07/09/2026).**

O fundador vai usar os módulos da Base UNIQ (**CRM, Financeiro e os demais necessários**) para operar a própria UNIQ — inclusive o controle das datas de faturamento dos co-fundadores.

**Por que isso é estratégico**
1. **Força qualidade:** módulo que o fundador usa todo dia não pode quebrar.
2. **Gera case interno:** a UNIQ vira prova de que a própria metodologia funciona.
3. **Economiza ferramenta:** não precisa contratar CRM/financeiro externo.
4. **Amplia o laboratório:** HQ Gráfica + Doceê + UNIQ = **3 operações reais** testando o mesmo sistema.

## 🤖 A Melissa

A Melissa é o **Parceiro Digital** da UNIQ. Ela atua em dois canais:

1. **WhatsApp/Instagram** — atendimento direto ao cliente final do parceiro
2. **Base UNIQ** — mentora e guia do próprio parceiro empreendedor

Ambos os canais compartilham a mesma memória no Supabase. A Melissa sempre sabe o contexto, independente de onde a conversa aconteça.

### Papéis da Melissa
- **SDR:** qualifica leads na pré-venda
- **Atendente:** responde clientes do parceiro
- **Mentora:** guia o parceiro no onboarding e trilhas
- **Coletora de dados:** extrai informações do lead no "Interrogatório" da MEL

### Comunicação e Atuação da Melissa

**Persona**
- Amiga, prestativa, conhecedora de Suzano.
- Fala como uma pessoa real, não como robô.
- Tem presença humana: vídeos no YouTube com rosto e voz (lipsync), posts em redes sociais.
- É a "garota propaganda" da UNIQ — aparece no site, Instagram, LinkedIn e YouTube.

**Atuação no WhatsApp/Instagram do parceiro**
- Responde mensagens dos clientes finais.
- Tira dúvidas, anota pedidos, organiza informações.
- Faz comunicação ativa: mensagens agendadas, follow-ups, abordagem de novos leads.
- Deixa tudo quase pronto para o parceiro finalizar a venda ou o trabalho.

**Atuação na Base UNIQ — versão CRM**
- O parceiro vê as conversas que a Melissa tem com os clientes.
- O parceiro pode assumir uma conversa ou responder pela Base UNIQ (como um Chatwoot).
- Mensagens enviadas pela Base UNIQ chegam ao cliente final no WhatsApp/Instagram.

**Atuação na Base UNIQ — versão Consultoria**
- A Melissa enxerga os dados do parceiro: vendas, caixa, business model canvas.
- Tira dúvidas, dá ideias, atua como parceira de negócios consultiva.
- Aponta caminhos, mas não toma decisões.

**Primeiro contato com a UNIQ**
- A Melissa é a porta de entrada da UNIQ.
- Ela faz uma primeira consultoria usando SPIN Selling: identifica dores do empreendedor.
- Com as dores mapeadas, marca-se um retorno humano para apresentar plano de ação imediato.
- O fechamento do negócio é feito por humano, para o parceiro se sentir seguro.

### Limites da Melissa

- **Não toma decisões** — apenas aponta caminhos e recomenda.
- **Não compartilha informações entre parceiros** — cada parceiro tem seus dados isolados.

## 📌 Regras Importantes

- **16h/semana** de disponibilidade do fundador — otimizar cada minuto
- **Foco local:** Suzano/Alto Tietê — nada nacional
- **Qualidade > Velocidade** na Fase 1
- **Base UNIQ é container, não produto** — o cliente compra consultoria
- **Módulos ativados pela UNIQ** — o parceiro não escolhe ou configura
- **Validar antes de escalar** — fundadores são laboratório, não receita
- **Zero execução técnica pelo CEO** — delegar para CODER/CMO/COO
- **SDD sempre** — Research → PRD → SPEC → WIRE → Implementação. Sem WIRE aprovado, não se escreve código de tela. A documentação é o que garante que o agente construtor entenda o objetivo sem carregar todo o contexto.
- **Laboratório antes do cliente** — HQ Gráfica e Doceê validam internamente antes de qualquer demonstração externa. Nada vai para o cliente sem ter funcionado em casa.
- **Validação mobile via GitHub + Vercel** — todo commit precisa subir no GitHub e publicar na Vercel, porque o fundador valida pelo celular durante o dia (acesso via túnel do OpenCode). Acesso total ao computador só à noite. **Trabalho não publicado = trabalho não validável.**
- **`DESIGN.md` (raiz) é a fonte oficial de identidade** — em conflito de tokens, vale ele.
- **Wireframe no repositório, design real no OpenDesign** — no código entrega-se estrutura e função, não polimento visual.
- **Módulo default + vertical** — especificidade de ramo vira variante do módulo default (ex.: `CRM` → `CRM_OTICA`), nunca módulo isolado. Vertical só se for replicável para 2–3 negócios do nicho.
- **Dogfooding** — a UNIQ opera a si mesma na Base UNIQ (CRM, Financeiro e demais).
- **Ondas de 4 + 4** — a pausa entre ondas é sprint de productização, com meta de cortar o tempo de entrega pela metade.
- **Mock-first para demo (decisão 07/09/2026)** — as telas e listas devem funcionar com **dados mockados realistas por padrão**, para que seja possível **apresentar/explicar o produto mesmo com o banco vazio**. Quando o banco tiver dados reais, a UI **prioriza os dados reais**; o mock funciona só como *fallback* (estado vazio/sem integração). Regra:
  1. **Demo/validação:** tela abre com mock realista (nomes, CNPJs, telefones, endereços brasileiros plausíveis).
  2. **Dados reais:** ao persistir/existir dado no Supabase oficial (`krrkfgv...`), a tela mostra o real.
  3. **Estratégia:** hooks com *fallback* — tentam buscar no banco; se vazio/erro, usam mock. Assim a apresentação nunca fica com tela branca.
  4. Isso difere do antigo "mock/local-first" (que era só mock): agora é **mock como fallback**, não como substituição permanente.

          │                │                 │
    ┌─────┴─────┐    ┌─────┴─────┐     ┌─────┴─────┐
    │ Evolution │    │ Evolution │     │ Evolution │
    │ WhatsApp  │    │ WhatsApp  │     │ WhatsApp  │
    │ Doceê     │    │ HQ Gráfica│     │ Cliente N │
    └───────────┘    └───────────┘     └───────────┘

### Decisões de Arquitetura

| Aspecto | Decisão | Rationale |
|---------|---------|-----------|
| **N8N** | Mesma VPS para todos os clientes (por enquanto) | Custo/simplicidade; migrar para VPS dedicada ou robusta no futuro |
| **LLM** | OpenRouter (repassado ao cliente) | Custo variável proporcional ao uso |
| **Isolamento** | Workflow separado por cliente | Cada Melissa tem seu fluxo, memória e configuração |
| **Pedidos** | Entram como "aguardando" | Esposa valida antes de mudar status |

### Fluxo do Pedido Automático

```
Cliente manda msg no WhatsApp
    ↓
Evolution API → webhook → N8N (workflow do cliente)
    ↓
Melissa (LLM via OpenRouter) processa
    ↓
┌─────────────────────────────────────────┐
│  Tools disponíveis:                     │
│  • criar_cliente(nome, telefone)        │
│  • criar_pedido(cliente_id, itens, ...) │
└─────────────────────────────────────────┘
    ↓
Só chama tool se tiver TODOS os campos obrigatórios
    ↓
INSERT em me_venda (status: "aguardando")
    ↓
Pedido aparece na Base UNIQ
    ↓
Esposa valida → muda status → contabiliza
```

### Tools da Melissa (contrato)

| Tool | Campos obrigatórios | Campos opcionais |
|------|---------------------|------------------|
| `criar_cliente` | `nome`, `telefone` | `email`, `documento` |
| `criar_pedido` | `cliente_id`, `itens[]`, `valor_total` | `observacoes`, `forma_pagamento` |

> **Nota:** Para `criar_pedido` com itens estruturados, ideal ter produtos cadastrados (`me_produto`). Alternativa: descrição livre com valor total.

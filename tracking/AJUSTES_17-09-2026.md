### 📌 Item 4 — Deletar pedido cancelado

**Pedido:** *"Quero ter a opção de deletar um pedido cancelado"*

**Feature nova com ação destrutiva → exige SDD (PRD → SPEC → WIRE).**

**Fatos do banco (verificados):** apagar `me_venda` **cascateia** para três tabelas filhas:

| Filha | `delete_rule` | Consequência |
|---|---|---|
| `me_itens_venda.venda_id` | **CASCADE** | itens somem junto ✅ |
| `me_venda_historico.venda_id` | **CASCADE** | histórico/timeline some junto |
| `me_contas_receber.venda_id` | **CASCADE** | ⚠️ **a conta a receber some junto** |

**Dois riscos que exigem decisão do fundador:**

1. **Financeiro:** se o pedido cancelado já teve conta a receber **paga**, o delete apaga um registro de dinheiro que **entrou de verdade** — o DRE e o Fluxo de Caixa perdem o lançamento.
   - ❓ Opção A: só permitir deletar com conta **em aberto**. ❓ Opção B: permitir sempre (aceita o furo).
2. **Estoque:** a RPC `registrar_venda` **baixa o estoque** (`UPDATE me_produto SET estoque_atual = estoque_atual - v_quantidade`). Deletar o pedido **não devolve** — o estoque fica descontado para sempre.
   - ❓ Opção A: devolver o estoque no delete. ❓ Opção B: não devolver.

**Decisão estrutural:**

| | Hard delete (`DELETE`) | Soft delete (arquivar) |
|---|---|---|
| Efeito | some do banco + cascata nas 3 filhas | sai da lista, registro preservado |
| Auditoria | perde tudo | preserva |
| Risco financeiro | alto | nenhum |
| Complexidade | baixa | média (filtro `deletado_em` em ~4 hooks) |

**Recomendação do agente:** **soft delete** escopado a pedidos `cancelado`. O pedido é um documento com valor contábil; apagar de verdade é o único caminho para perder dinheiro sem querer. O efeito percebido na tela ("sumiu da lista") é o mesmo.

**❓ Também definir:** onde fica o botão (detalhe, lista, ou os dois) · confirmação obrigatória · se exige cargo/permissão · o que fazer se o pedido `cancelado` tiver conta paga.

**Lane:** pedidos — **não colide** com produtos.

### 📌 Item 7 — ✅ WhatsApp/n8n sempre "Cartão de Crédito" (causa confirmada)

**Pedido:** *"Pedidos registados pelo N8N (whatsapp) via RPC sempre apresentam como forma de pagamento cartão de crédito"*

**Boa notícia: o banco está certo. O bug é SOMENTE de exibição.**

#### A verdade está no banco (`me_forma_pagamento`)

| id | nome |
|---|---|
| 1 | Dinheiro |
| 2 | **Cartão de Crédito** |
| 3 | **Pix** |
| 4 | Cartão de Débito |
| 5 | Boleto |
| 20/21/22 | Dinheiro / Cartão de Crédito / Pix — **linhas do tenant `6257ebef`** |

#### Os mapas do app divergem da tabela

**LEITURA — ids 2 e 3 invertidos** (duas cópias idênticas, ambas erradas):
- `use-pedidos.ts:43-51`
- `use-pedido.ts:77-85`

```js
1: "dinheiro",  2: "pix",  3: "cartao_credito",  4: "cartao_debito",  5: "boleto"
              ↑ trocado       ↑ trocado
```

**Prova nos dados reais:** os pedidos do n8n estão gravados com `forma_pagamento = 3` — que na tabela é **Pix**. O leitor converte 3 em `"cartao_credito"`. **É exatamente o sintoma relatado.** Os pedidos do WhatsApp estão **corretos** no banco como Pix.

**Segundo caminho para o mesmo sintoma:** as duas funções terminam com
```js
return map[codigo || 3] || "cartao_credito";
```
→ **qualquer pedido com forma de pagamento nula também aparece como "Cartão de Crédito"**.

**ESCRITA — duas entradas erradas** (`use-criar-pedido.ts:28-34`):

| chave | valor hoje | deveria ser | efeito |
|---|---|---|---|
| `cartao_debito` | 2 | **4** | débito gravado como crédito |
| `boleto` | 3 | **5** | boleto gravado como Pix |

(`dinheiro:1`, `cartao_credito:2`, `pix:3` já estão certos.)

#### Raiz do problema

Existem **três mapas hardcoded** de uma tabela que **já existe no banco** (`me_forma_pagamento`), e eles divergem. Cada lugar que "sabe" os ids por conta própria é um novo ponto de divergência.

**Plano de correção:**
- **Agora (hotfix):** corrigir os 2 mapas de leitura + o fallback + as 2 entradas da escrita. Não exige migration.
- **Estrutural (depois):** hook `use-formas-pagamento` lendo `me_forma_pagamento` (linhas globais + da empresa) como **fonte única** para ler, escrever e popular o `<select>`. Mata a classe do bug.

#### 🐞 Achado extra na RPC `registrar_venda` (mesma revisão)

`SELECT id INTO v_forma_pagamento_id FROM me_forma_pagamento WHERE nome ILIKE v_forma_pagamento LIMIT 1`
- **Sem filtro de empresa** — e agora existem linhas globais (1–5) **e** do tenant `6257ebef` (20–22) com os mesmos nomes.
- **`LIMIT 1` sem `ORDER BY`** → qual id volta é **indefinido**. Se voltar 20–22, a leitura não conhece esses ids e cai no fallback → "Cartão de Crédito" de novo (mesmo depois de corrigir os mapas).
- **Incoerência interna:** o texto cai para `'PIX'` mas o id cai para `1` (**Dinheiro**). Ou o fallback é Pix, ou é Dinheiro — hoje a venda e a conta a receber discordam.
- Observação: `me_venda.forma_pagamento` guarda o **id (integer)**; `me_contas_receber.forma_pagamento` guarda o **nome (texto)**. Duas representações do mesmo conceito.

**Tipo:** bug · **Sem SDD** (correção de mapa) · **Lane:** pedidos
